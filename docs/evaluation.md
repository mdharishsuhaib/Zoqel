# Zoqel — Evaluation Methodology

## Overview

Zoqel's evaluation strategy is designed to produce honest, reproducible, defensible metrics.
The final numbers come from a held-out test set that was never used during training or validation.

---

## The Core Principle

> A model that has seen its test set produces impressive-but-meaningless metrics.
> Zoqel's numbers come from data the model has never seen.

---

## Dataset Construction

### Source
10,000 synthetic transactions generated by `ml/generate_dataset.py`.

### Distribution
| Failure Reason | Share | Base Recovery Probability |
|---|---|---|
| BANK_TIMEOUT | 28% | 80% |
| NETWORK_ERROR | 22% | 75% |
| INSUFFICIENT_FUNDS | 20% | 5% |
| EXPIRED_CARD | 13% | 10% |
| REPEATED_FAILURE | 10% | 15% |
| UNKNOWN | 4% | 30% |
| DUPLICATE_ATTEMPT | 3% | 0% |

### Split
```
10,000 transactions
       │
       ├── 70%  (7,000)  → transactions_train.csv   [model training]
       ├── 15%  (1,500)  → transactions_val.csv     [hyperparameter tuning]
       └── 15%  (1,500)  → transactions_test.csv    [HELD-OUT — final evaluation only]
```

The test set is loaded once — in `evaluate.py` — and never used during training.

---

## Ground Truth

Recovery outcomes (`recovery_outcome` column) are determined using the same deterministic
algorithm as the Java `PaymentSimulator`:

```
Random(simulatorSeed + 2 * 31337L).nextDouble() < base_recovery_probability
```

Where `base_recovery_probability` depends on `failure_reason` and is modestly adjusted
by customer payment history (success rate, failure count).

This ensures the ML model is trained on realistic, consistent data — not arbitrary labels.

---

## ML Metrics

Zoqel reports these metrics from the held-out test set:

| Metric | Definition | Why it matters |
|---|---|---|
| **Precision** | TP / (TP + FP) | How often a "recoverable" prediction is actually correct |
| **Recall** | TP / (TP + FN) | How much recoverable revenue we avoid missing |
| **F1** | Harmonic mean of P and R | Overall model quality |
| **AUC-ROC** | Area under ROC curve | Discriminative power across thresholds |
| **False Positive Rate** | FP / (FP + TN) | Rate of unnecessary interventions |
| **False Negative Rate** | FN / (FN + TP) | Rate of missed recoveries |

---

## Business Metrics

More important than ML metrics for Razorpay's evaluation:

| Metric | Definition |
|---|---|
| **Revenue at Risk (₹)** | Total amount of all failed transactions evaluated |
| **Truly Recoverable (₹)** | Amount that was actually recoverable (ground truth) |
| **Revenue Recovered (₹)** | Amount from transactions where Zoqel correctly predicted and executed recovery |
| **Revenue Missed (₹)** | Amount from false negatives (recoverable, but Zoqel predicted not) |
| **False Intervention Cost (₹)** | Amount from false positives (not recoverable, but Zoqel tried) |
| **Recovery Rate** | Revenue Recovered / Truly Recoverable |

---

## Cost of False Positives

Unlike most ML problems, Zoqel's false positives have a real cost:

- **True Positive**: +₹amount recovered
- **False Positive**: Intervention attempt on an unrecoverable transaction
  (operational cost, potential customer friction)
- **False Negative**: ₹amount permanently lost

The evaluation explicitly reports the ₹ value tied to false positives (see `revenue_falsely_intervened_paise`)
so the cost is visible, not hidden.

---

## Expected Value Framework

The optimal threshold for Zoqel is not the one that maximizes F1.
It is the one that maximizes:

```
Expected Value = P(TP) × Revenue_Recovered
               - P(FP) × Intervention_Cost
               - P(FN) × Revenue_Lost
```

For the Razorpay demo, we use the default threshold (0.5) and the policy engine's
confidence threshold (0.75) as the safety boundary.

## How to Reproduce Results

```bash
# Step 1: Generate dataset (always run first)
cd ml
python generate_dataset.py

# Step 2: Train model (uses train.csv + val.csv)
python train_model.py

# Step 3: Evaluate on held-out test set (uses test.csv only)
python evaluate.py
```

All three scripts use `RANDOM_SEED = 42` for reproducibility.
Running them on any machine produces identical results.

## Batch Evaluation (Stage 6)

In Stage 6, the complete end-to-end recovery workflow (not just the ML model) is evaluated:

1. All 1,500 test transactions are imported into the backend
2. `POST /api/recovery/process/{transactionId}` is called for each FAILED transaction
3. The actual recovery outcomes (from the payment simulator) are compared to the
   ground truth labels
4. Dashboard metrics at `GET /api/dashboard/metrics` reflect the real workflow outcomes

This produces **two sets of metrics**:
- **ML-only** (from `evaluate.py`): model prediction quality
- **End-to-end** (from batch run): full system performance including policy decisions,
  agent recommendations, and simulator outcomes

Both sets of metrics are reported honestly, including cases where the policy engine
blocked a correct agent recommendation.
